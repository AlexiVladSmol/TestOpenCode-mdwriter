# План исправлений mdwriter

Рабочий план исправлений по итогам ревью кода (ноябрь 2026, коммит `7080a56`).
Файл написан так, чтобы по нему мог работать как человек, так и LLM-агент:
у каждой задачи есть ID, приоритет, зависимости, затрагиваемые файлы,
описание проблемы, требуемые изменения, критерии приёмки и тесты.

## 0. Правила для исполнителя (обязательно прочитать)

1. **Одна задача — один коммит.** В том же коммите отметьте задачу `[x]`
   в таблице «Карта задач» ниже. Не смешивайте задачи.
2. **Порядок и исполнитель.** Берите только задачи, где в колонке
   «Исполнитель» указана ваша модель, и идите по этапам из раздела
   «Распределение и этапы». Учитывайте поле «Зависит от». Задачи другого
   исполнителя не трогайте, даже если они кажутся простыми.
3. **Ссылайтесь на код по именам функций/типов, а не по номерам строк** —
   номера строк сдвигаются после каждой задачи. В этом плане функции
   указаны как `файл::функция`.
4. **Проверка перед коммитом** (из корня репозитория):
   ```powershell
   cargo fmt --all
   cargo clippy --workspace --all-targets -- -D warnings
   cargo test --workspace
   ```
   Если сборка невозможна (например, нет компоновщика), **остановитесь и
   сообщите**, не коммитьте непроверенный код.
5. **Сначала тест, потом исправление.** Для каждого бага — регрессионный
   тест, который падает до исправления и проходит после. UI-логику выносите
   в чистые функции, чтобы её можно было тестировать без egui.
6. **Зависимости.** Новые крейты добавлять только если они названы в задаче.
   Версии — в `[workspace.dependencies]` корневого `Cargo.toml`.
7. **Стиль.** Комментарии и строки интерфейса — на русском, как в текущем
   коде. Сообщения коммитов — на английском в стиле истории репозитория:
   `fix: ...`, `feat: ...`, `refactor: ...`, `docs: ...`, `ci: ...`
   (в конце — ID задачи, например `fix: flush note on exit (A1)`).
8. **Не расширяйте область задачи.** Заметили другой баг — допишите его в
   раздел «Найдено по ходу» в конце файла, а не чините молча.
9. **Не ломайте формат данных пользователя.** Заметки — обычные `.md`;
   никакой служебной информации в них не писать.
10. **Подпись коммитов (обязательно).** Репозиторий публичный, и GitHub
    приписывает коммит аккаунту, которому принадлежит адрес автора.
    Адрес `deepseek@users.noreply.github.com` принадлежит **чужому**
    аккаунту `deepseek` — использовать его нельзя. Каждый коммит делайте
    с явной подписью, не меняя глобальные настройки git:
    ```powershell
    git -c user.name="DeepSeek (via AlexiVladSmol)" -c user.email="358176669+AlexiVladSmol@users.noreply.github.com" commit -m "..."
    ```
    Для других моделей — то же самое, со своим именем в скобках:
    `user.name="<Модель> (via AlexiVladSmol)"`, адрес тот же. Не задавайте
    `user.name`/`user.email` через `git config` в общей рабочей копии — это
    поменяет подпись и у других исполнителей. Проверка после коммита:
    `git log -1 --format="%an <%ae>"`.

### Распределение и этапы

Claude берёт задачи, где ошибка ведёт к потере данных или где нужно
спроектировать поведение, а не просто реализовать спецификацию:
**A2, A3, B2, B7, C1, C3**. Остальное делает DeepSeek.

Задачи одного этапа можно делать параллельно: исполнители работают в
разных ветках и правят разные файлы. Следующий этап начинается, когда
предыдущий слит в `main`.

| Этап | Claude | DeepSeek | Почему так |
|---|---|---|---|
| 0 | — | E1, E3 | CI первым: дальше всё проверяется автоматически |
| 1 | A2 → A3 (`crates/app`) | A1, A4 → A5, B6 (`crates/vault`), B12, B3, B1 → D2 (`markdown`, `index`, `preview`) | A1 и A5 тоже правят `main.rs`, но в других функциях (`on_exit`, `open_vault`, `sync_settings`) — конфликт мал; при слиянии A1/A5 идут после A2/A3 |
| 2 | C1 (`crates/index`, `crates/graph`) | R1 (`crates/app`) | R1 трогает весь `main.rs`, поэтому в этапе 2 никто больше не правит `crates/app` |
| 3 | B7, затем B2 | B4, B5, B8, B9, B10, B11 | после R1 правки в `crates/app` разнесены по модулям; B7 меняет `watcher.rs` и обработку изменений в `state.rs` |
| 4 | C3 | C2, C4, B13, D3, D4, E2 | C3 и C2 оба меняют `crates/index` — C2 сливать после C3 |
| 5 | ревью | E4 | документация в конце |

Правило для ревью: задачи DeepSeek из фазы A и B4 (данные и безопасность)
перед слиянием смотрит Claude или человек.

## Фаза A — сохранность данных (P0)

### A1. Сохранять заметку при выходе и смене vault

- **Файлы:** `crates/app/src/main.rs` (`impl eframe::App for App::on_exit`, `App::open_vault`).
- **Проблема:** `on_exit` сохраняет только настройки. Текст, набранный за
  последнюю секунду (`AUTOSAVE_DELAY`), теряется при закрытии окна.
  `open_vault` заменяет `self.vault` без записи открытой заметки.
- **Сделать:**
  1. В `on_exit` перед `save_settings()` вызвать `flush()` у текущего
     `VaultState` (если есть).
  2. В `open_vault`, после того как диалог вернул путь и **до** замены
     `self.vault`, вызвать `flush()` у старого `VaultState`.
- **Приёмка:** набрать текст и сразу закрыть окно → после перезапуска текст
  на месте. То же при «Open vault…» на другую папку.
- **Тесты:** ручная проверка (UI); юнит-тест не требуется.

### A2. Не терять ошибки сохранения; уведомления в UI

- **Файлы:** `crates/app/src/main.rs` (`VaultState::flush`, `maybe_autosave`, все `eprintln!` в пользовательских операциях).
- **Проблема:** `flush` сбрасывает `dirty = false` даже при ошибке записи;
  ошибка уходит в `eprintln!`, а в release-сборке
  (`windows_subsystem = "windows"`) консоли нет — пользователь не узнает,
  что заметка не сохранена.
- **Сделать:**
  1. Добавить тип уведомления:
     ```rust
     enum NoticeLevel { Info, Error }
     struct Notice { text: String, level: NoticeLevel, shown_at: f64 }
     ```
     и поле `notices: Vec<Notice>` в `App` (или в `VaultState`, если удобнее
     передавать). Для доступа из `VaultState` — метод `fn notify(&mut self, level, text)`.
  2. `flush` возвращает `Result<(), String>`; при ошибке **оставляет
     `dirty = true`**. `maybe_autosave` при ошибке ставит
     `last_edit = Some(now)`, чтобы повтор был через `AUTOSAVE_DELAY`, а не в
     каждом кадре, и публикует уведомление (не чаще одного одинакового
     сообщения подряд).
  3. Отрисовка: `egui::Area` с якорем `Align2::RIGHT_BOTTOM`, порядок
     `Order::Foreground`. `Info` скрываются через 5 с, `Error` — висят до
     клика по «✕».
  4. Все `eprintln!` в действиях пользователя (создание, чтение, сохранение,
     экспорт, открытие vault, ошибка watcher) дублировать уведомлением.
     `eprintln!` можно оставить для отладки.
  5. Индикатор `●` у имени файла показывать красным, если последняя попытка
     сохранения завершилась ошибкой.
- **Приёмка:** сделать файл заметки только для чтения → ввести текст →
  появляется ошибка, `●` остаётся, после снятия атрибута заметка сохраняется
  автоматически.

### A3. Обработка внешних изменений открытой заметки

- **Зависит от:** A2.
- **Файлы:** `crates/app/src/main.rs` (`VaultState::{load, flush, rescan, ui_editor}`).
- **Проблема:** при изменении файла извне (git, синхронизация, другой
  редактор) `rescan` не перечитывает открытую заметку: в редакторе остаётся
  старый текст, и автосохранение затирает чужие изменения. Если файл
  удалён/переименован извне, несохранённый буфер молча выбрасывается.
- **Сделать:**
  1. Поле `disk_text: Option<String>` — содержимое файла на момент последнего
     чтения (`load`) или успешной записи (`flush`).
  2. Поля `conflict: bool` и `orphaned: bool`.
  3. В `rescan` для открытой заметки:
     | Состояние | Действие |
     |---|---|
     | файл есть, содержимое == `disk_text` | ничего |
     | файл есть, отличается, `!dirty` | перезагрузить `editor_text`, обновить `disk_text`, уведомление Info «Заметка обновлена с диска» |
     | файл есть, отличается, `dirty` | `conflict = true` |
     | файла нет, `!dirty` | закрыть, как сейчас |
     | файла нет, `dirty` | **не закрывать**, `orphaned = true` |
  4. В `flush` перед записью перечитать файл и сравнить с `disk_text`; если
     отличается — не писать, выставить `conflict = true` (защита от гонки,
     когда watcher ещё не сработал).
  5. Пока `conflict || orphaned`, автосохранение отключено. Над редактором
     показывать полосу с кнопками:
     - конфликт: «Загрузить с диска (мои правки пропадут)» / «Оставить мои
       (перезаписать файл)»;
     - удалён: «Сохранить снова» / «Закрыть без сохранения».
- **Приёмка:** (а) без несохранённых правок изменить файл в другом редакторе
  → текст в mdwriter обновился; (б) с несохранёнными правками — появилась
  полоса конфликта, файл на диске не перезаписан, обе кнопки работают;
  (в) удалить открытый файл с несохранёнными правками — буфер не потерян.
- **Тесты:** вынести решение из таблицы п.3 в чистую функцию
  `fn reconcile(disk: Option<&str>, known: Option<&str>, dirty: bool) -> Reconcile`
  и покрыть юнит-тестами все 5 строк таблицы.

### A4. Надёжная атомарная запись

- **Файлы:** `crates/vault/src/store.rs` (`Vault::write`, `temp_path`).
- **Проблема:** нет `fsync` перед `rename` (после сбоя питания возможен
  пустой файл); временный файл всегда `name.md.tmp` (коллизии, не скрыт от
  обхода и наблюдателя); при ошибке временный файл остаётся.
- **Сделать:**
  1. Вынести публичную функцию `pub fn atomic_write(path: &Path, bytes: &[u8]) -> std::io::Result<()>`
     (её же использует A5).
  2. Имя временного файла: `.{имя_файла}.{pid}.{счётчик}.tmp` в той же папке
     (точка в начале — файл скрыт для `list_notes` и фильтра B7; счётчик —
     `static AtomicU64`).
  3. `File::create` → `write_all` → `sync_all` → `drop` → `fs::rename`.
  4. При любой ошибке — `let _ = fs::remove_file(&tmp)` и вернуть ошибку.
  5. Windows: если `rename` вернул `PermissionDenied` (файл держит антивирус
     или синхронизатор), повторить до 3 раз с паузой 50 мс.
  6. `Vault::create`: заменить проверку `exists()` + `write` на
     `OpenOptions::new().write(true).create_new(true)`; ошибку
     `AlreadyExists` считать успехом.
- **Приёмка / тесты:** существующий `atomic_write_and_read` проходит;
  новый тест: двойная запись даёт последнее содержимое, в папке нет файлов
  `*.tmp`; тест `create` не перезаписывает существующий файл.
- **Документация:** в README не обещать больше, чем гарантирует реализация.

### A5. Атомарная и редкая запись настроек

- **Зависит от:** A4.
- **Файлы:** `crates/app/src/main.rs` (`App::{sync_settings, save_settings}`).
- **Проблема:** настройки пишутся `fs::write` (не атомарно) и при
  перетаскивании разделителя — в каждом кадре.
- **Сделать:** писать через `vault::store::atomic_write`; в `sync_settings`
  сохранять только если `settings_dirty` и не зажата кнопка мыши
  (`!ctx.input(|i| i.pointer.any_down())`). `on_exit` сохраняет всегда.
- **Приёмка:** при перетаскивании разделителя файл настроек пишется один раз
  после отпускания мыши.

## Фаза B — корректность (P1–P3)

### B1. Wikilinks с пробелами кликабельны

- **Файлы:** `crates/preview/src/lib.rs` (`wiki_links_to_md`); после D2 — `crates/markdown`.
- **Проблема:** `[[Моя заметка]]` превращается в
  `[Моя заметка](wiki:Моя заметка)`; по CommonMark адрес ссылки не может
  содержать пробел → ссылка рендерится обычным текстом.
- **Сделать:** генерировать адрес в угловых скобках:
  `[label](<wiki:target>)`. В `label` экранировать `\`, `[`, `]` обратным
  слешем. Если `target` содержит `<`, `>` или перевод строки — не
  преобразовывать эту ссылку (оставить исходный текст).
- **Тесты:** парсить результат `pulldown_cmark::Parser` и проверить, что
  есть `Event::Start(Tag::Link { dest_url, .. })` с
  `dest_url == "wiki:Моя заметка"`; кейсы: пробел, алиас с `]`, цель с
  `#заголовок`. Обновить существующий тест `wiki_links_transformed`.

### B2. Переключение задач по байтовому смещению

## Найдено по ходу

_Сюда исполнители дописывают новые проблемы: ID-кандидат, файл/функция,
описание, как воспроизвести._

- **G1 (P1, найдено при A2). Нет запасного рендерера без OpenGL.**
  `main()` в `crates/app` — eframe собран только с `glow`. На машине без
  OpenGL 2.0 (виртуалки, RDP, старые драйверы) приложение сразу
  завершается: `OpenGL(PainterError("egui_glow requires opengl 2.0+. "))`,
  а в release-сборке пользователь даже не увидит сообщения. Предложение:
  включить feature `wgpu` (DirectX 12 / Vulkan) и при ошибке glow
  перезапускать `run_native` с `Renderer::Wgpu`; ошибку старта показывать
  через `rfd::MessageDialog`. С `wgpu` приложение на такой машине
  запускается (проверено).
- **G2 (P2, найдено при A2). Значки из шрифта рисуются «квадратиками».**
  Встроенные шрифты egui 0.37 не содержат `●`, `☑`, `❝`, `⚠`, `✕` —
  на панели форматирования кнопки «Задача» и «Цитата» пустые. В A2
  индикатор заменён на `•`, а уведомления используют только текст.
  Нужно: проверить остальные символы интерфейса (`✕` у поиска, `—`) и
  заменить на текст или подключить шрифт с этими символами.
- **G3 (P1, организационное). Репозиторий не отформатирован rustfmt**
  (~40 расхождений в 7 файлах до любых правок). `cargo fmt --all` по
  правилу 4 переформатирует чужие участки и вызовет конфликты между
  ветками. До слияния этапа 1 форматировать только изменённые строки;
  общий `cargo fmt --all` — отдельным коммитом после этапа 1, тогда же
  включить `fmt --check` в CI (E1).
  **Решено** вместе с N1: после слияния этапа 1 весь репозиторий
  отформатирован; с этого момента правило 4 (`cargo fmt --all`) действует
  в полном объёме.
- **G4 (P0, стык A1 и A3 — сделать при слиянии этапа 1).** После A3
  `VaultState::flush` при конфликте или удалённом файле **не пишет** на
  диск и возвращает ошибку. Поэтому в `on_exit` и `App::open_vault`
  (задача A1) нужно вызывать не `flush()`, а
  `VaultState::flush_or_copy()`: при конфликте он сохраняет правки копией
  `имя (конфликт).md`, иначе ведёт себя как `flush()`. Сейчас метод помечен
  `#[allow(dead_code)]` — снять пометку при подключении.
  **Решено** в коммите слияния этапа 1: оба места вызывают
  `flush_or_copy()`, он же делает копию и при ошибке записи; `open_vault`
  не меняет vault, если сохранить не удалось.
- **N1 (E1, блокирует зелёный CI).** `crates/app/src/main.rs` не приведён к
  выводу `rustfmt` (файл, видимо, писался вручную: `#[derive(Default)]`
  отдельной строкой, переполнения строк, вложенность в `ui()`), поэтому
  `cargo fmt --all -- --check` падает на нём. Остальные крейты отформатированы
  в коммите E1. Воспроизведение: `cargo fmt --all -- --check` → диффы только в
  `main.rs`. Нужен отдельный коммит «только форматирование» после слияния
  правок A2/A3 (в этапе 1 файл параллельно правит Claude, поэтому DeepSeek
  его не переформатировал).
  **Решено:** отдельный коммит `style: rustfmt main.rs` сразу после слияния
  этапа 1.
- **N2.** `crates/vault/src/store.rs::tests::temp_dir` (и аналогичные хелперы в
  `crates/index`) создают каталоги в `%TEMP%` и никогда их не удаляют — они
  накапливаются после каждого `cargo test`. Кандидат: писать тестовые vault в
  общий временный корень и чистить по завершении.
- **N3.** `crates/index/src/lib.rs::Index::build` кладёт в `contents` полный
  текст заметки, включая frontmatter, а `search` ищет по этому тексту. Запрос
  по служебному ключу (`title`, `tags`) даёт совпадение во всех заметках, где
  такой ключ есть. Воспроизведение: заметка с `tags: пони` → поиск «tags»
  находит её. Кандидат: индексировать тело (после `split_frontmatter`) — можно
  учесть в C2.

- **G5 (организационное, найдено при ревью R1).** Коммиты DeepSeek этапов
  0–2 подписаны `deepseek@users.noreply.github.com`, и GitHub показывает их
  автором чужой аккаунт `deepseek`. Историю `main` не переписываем
  (публичный репозиторий, force push сломал бы чужие копии и PR); для новых
  коммитов действует правило 10 раздела 0.
